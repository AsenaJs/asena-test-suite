## Recommendation for P1.static.010 / P1.static.011

Both adapters keep every file outside the root private, so the security property holds everywhere; the difference is the answer.
Recommended contract (ergenecore's behaviour, `Ergenecore.ts:1575-1599`): the static step decodes the request path once; a malformed
escape is a client error (**400**, through the normal `HttpException` path so `onError` sees it); a decoded path that leaves the root
is refused (**403**, logged); everything else that names no file is the not-found path (404, `onNotFound`). Reasons: a malformed
escape is a syntactically wrong request, not a missing resource (RFC 3986 section 2.1); 403 separates "refused" from "absent" in
logs; and hono's rule also 404s real files whose names need a reserved escape (any static path that still holds `%` after
`decodeURI`, `serve-static/index.js:27`). One hono code path produces both 404s, so one flag covers both rows. **Maintainer
decision** (PLAN section 14): if the maintainer prefers 404 for both, the flag moves to ergenecore and WP-62 is rewritten against
`Ergenecore.ts` (chain after WP-55).

How WP-07b applies it: P1.static.010 keeps the no-leak assertions for all nine targets ungated (a leak can never hide behind a
divergence flag) and pins the six agreed 404s; the three encoded-slash statuses move to P1.static.011, which pins 400 for the
malformed escapes and 403 for the encoded-slash targets and is gated by `static.encodedPathIsDecodedAndChecked` (hono).
